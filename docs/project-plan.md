# 项目编写计划

## 项目目标

构建一个面向 Web UI 自动化测试场景的 AI 增强测试平台，优先解决以下问题：

- 测试步骤表达不统一
- 元素定位不稳定
- 执行失败缺乏可解释证据
- 用例、套件、执行记录缺乏统一管理

## 项目定位

项目定位为“AI 增强型自动化测试执行平台”，不是通用浏览器 Agent。

一期核心目标：

- 结构化 DSL 执行
- 步骤级证据报告
- 平台化用例与报告管理
- DOM 增强定位基础版

二期增强目标：

- 自然语言生成 DSL
- Vision 辅助定位
- AI 失败归因与总结

## 分阶段计划

### 阶段 1：基础平台与执行链路

目标：

- 建立前后端基础工程
- 打通最小执行闭环

范围：

- FastAPI 基础工程
- React 前端基础工程
- 登录接口与基础权限模型
- DSL Schema 定义
- 基础动作执行：`goto`、`click`、`input`、`wait_for`、`assert_text`、`assert_url_contains`
- 单个 Case 执行
- JSON 报告输出

交付物：

- 可运行的前后端工程骨架
- 一条登录冒烟用例
- 基础执行结果页

验收标准：

- 能创建或导入一份 DSL 用例
- 能触发执行并看到结构化结果
- 非法 DSL 能在执行前被拦截

### 阶段 2：平台化管理与报告展示

目标：

- 让系统具备平台可用性

范围：

- 用例管理页
- Suite 管理页
- 执行任务列表
- 报告列表与详情页
- HTML 报告导出
- 本地文件证据管理

交付物：

- 可管理的 Case/Suite 页面
- 报告查看与导出能力
- 执行历史记录

验收标准：

- 能批量执行 Suite
- 能查看单次任务详情
- 能导出基础报告

### 阶段 3：增强定位与调试工作台

目标：

- 提升测试可维护性与执行稳定性

范围：

- DOM 候选召回
- 候选打分与命中记录
- visible/enabled 校验
- 候选回退策略
- 工作台页面中的页面预览与元素调试区

交付物：

- 基础 Locator 服务
- 工作台调试面板
- 定位证据展示

验收标准：

- 语义 target 能命中简单页面元素
- 报告中可查看候选与最终命中信息

### 阶段 4：AI 增强能力

目标：

- 提高编写效率与复盘效率

范围：

- 自然语言生成 DSL
- 报告 AI 总结
- Vision 排序接口预留或原型实现

交付物：

- AI 辅助生成入口
- AI 分析结果展示

验收标准：

- 生成 DSL 必须通过 schema 校验
- AI 输出仅做辅助，不绕过核心执行链

## 任务拆分原则

- 每次只做一个清晰子目标
- 先定义类型与接口，再写逻辑
- 先保证后端 API 与数据模型稳定，再推进复杂前端交互
- 所有关键链路都要有最小测试

## 风险与兜底方案

### 风险 1：自然语言生成不稳定

兜底：

- 一期采用手写 DSL 和模板辅助

### 风险 2：SQLite 与 PostgreSQL 行为差异

兜底：

- 模型设计尽量贴近 PostgreSQL
- 关键 SQL 行为尽早在 PostgreSQL 验证

### 风险 3：元素定位复杂度过高

兜底：

- 一期先做 DOM 增强版
- Vision 仅保留接口

### 风险 4：前端页面过早追求复杂可视化

兜底：

- 第一版优先保留任务流、报告流和工作台主链路

## 开发顺序建议

1. 后端基础工程与数据库模型
2. DSL Schema 与执行引擎
3. 执行任务与报告接口
4. 前端平台骨架与路由
5. 用例管理页与执行中心
6. 报告页与导出
7. 工作台调试能力
8. AI 增强能力

## 验证策略

后端：

- 单元测试覆盖 Schema、服务层、Locator 基础逻辑
- 集成测试覆盖任务创建、执行、报告查询

前端：

- 组件测试覆盖表单、列表、状态展示
- 页面测试覆盖用例创建、任务查看、报告查看

端到端：

- 至少保留一条登录冒烟用例作为主回归链路
